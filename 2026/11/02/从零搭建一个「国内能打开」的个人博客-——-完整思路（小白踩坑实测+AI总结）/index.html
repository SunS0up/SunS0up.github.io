从零搭建一个「国内能打开」的个人博客 —— 完整思路（小白踩坑实测+AI总结）

发表于2026-11-02|更新于2026-11-02
|浏览量:

写于 2026-11-02。本文不是泛泛的教程，而是把这套站真正跑通后回填的决策思路 + 踩坑记录。

按这个方法搭，成品形态：https://<你的用户名>.github.io/，零成本、自动 HTTPS、国内直连可开。

全程实测环境：Windows + Node 24.21.0 + Hexo 8.1.2 + Butterfly 5.7.1。

0. 一句话结论

用 Hexo 写、用 Butterfly 美化、用 GitHub Pages 托管。

不要一上来就想 Vercel / 自定义域名 —— 这两个是后话，而且极可能让你的站「在全球可用、在国内打不开」。

1. 三个硬约束，先想清楚再选技术

搭站之前先问自己三件事，答案直接决定选型：

| 约束 | 你的情况 | 影响 |

| — | — | — |

| 要不要花钱 | 不花 | 排除自己买服务器 / 云主机 |

| 访客主要在哪 | 国内 | 这是最狠的一条，直接砍掉一半方案 |

| 谁维护 | 我自己，偶尔写文章 | 越少运维越好，最好是 git push 就完事 |

1.1 选型对比（实测结论，不是理论）

| 方案 | 国内可访问 | 成本 | 结论 |

| — | — | — | — |

| GitHub Pages | ✅ 实测可连 | 免费 | 选它 |

| Vercel | ❌ *.vercel.app 被 DNS 污染 | 免费 | 只在能稳定挂代理时考虑 |

| Cloudflare Pages | ⚠️ *.pages.dev 同样不稳 | 免费 | 备选 |

| Netlify | ⚠️ 不稳 | 免费 | 备选 |

| 国内云 + 备案 | ✅ 最稳 | 服务器费 + 备案周期 | 认真做站再考虑 |

1.2 为什么「Vercel + 自定义域名」这条路被我放弃了

原本的打算是 Vercel 配 xxx.vercel.app，再绑一个免费域名 xxx.cc.cd。实测两个都死，而且死法不同：

① vercel.app —— DNS 污染

同一时刻查同一个域名，国内 DNS 和真实 IP 完全不同：

| 查询来源 | 返回 IP | 真相 |

| — | — | — |

| 本机 / 阿里公共 DNS | 31.13.69.169 | 这是 Facebook 的 IP，纯属伪造 |

| 阿里 DNS 查 vercel.app 顶级 | 202.182.98.125 | 同样是假地址 |

| 外部服务（非中国网络）访问该站 | HTTP 200，标题正确 | 站点本身完全正常 |

结论：Vercel 那边部署得好好的，是 DNS 把国内访客送到假 IP 上。换 DNS、换 Wi-Fi、用流量都没用。

② cc.cd 域名 —— SNI 层整段封锁

做了一组对照实验（同一个 IP、只换 SNI）：

| 目标 | IP | SNI | 结果 |

| — | — | — | — |

| cc.cd | 13.250.16.35（AWS 新加坡，与 Vercel 无关） | cc.cd | ECONNRESET |

| 同一个 IP | 13.250.16.35 | example.com | ✅ 握手成功 |

| 同一个 IP | 13.250.16.35 | amazonaws.com | ✅ 握手成功 |

同一台服务器，TLS 握手里只要带 cc.cd 就被重置，换个域名就通 —— 说明封的是域名后缀本身，跟主机、IP、配置全都无关。

教训：免费域名后缀（cc.cd、de5.net 这类）因为滥用严重，整段进了黑名单。换什么托管都救不回来。要自定义域名，就买 .com / .net / .top，几十块一年，别省这个钱。

2. 整体架构

关键认知：仓库里不放主题源码，只放构建成品。

| 角色 | 负责什么 | 你不需要操心什么 |

| — | — | — |

| Hexo | Markdown → HTML | 数据库、后端、服务器 |

| Butterfly 主题 | Pug 模板 + Stylus 样式 → 页面外观 | 手写 CSS |

| GitHub 仓库 | 存成品 + 当版本备份 | 买服务器、配 Nginx |

| GitHub Pages | 托管 + HTTPS 证书 + CDN | 部署脚本、证书续期 |

实测：本地主题源码 217 个文件，推到仓库的成品只有 21 个文件（含 css/index.css 204 KB —— 那就是主题的 Stylus 编译结果）。

4. 上线：三条发布路径

路径 A：hexo deploy（日常用这个）

原理：hexo-deployer-git 把 public/ 复制进 .deploy_git，提交后 git push --force 到 main。

优点：一条命令。缺点：force push，且不保证触发 Pages 构建（实测三次部署，零次触发）。

路径 C：GitHub Actions 自动构建（最省心的长期方案）

仓库里存源码，push 后由 Action 跑 hexo generate 并发布。优点：push 必触发、不需要本地构建、换电脑无影响。代价：一次性配置成本 + Pages 源要切成「GitHub Actions」。

建议：先用 A 跑通，站点稳定后再升到 C。

6.1 .nojekyll 一直部署不上去

6.3 force push 之后 Pages 不重建

现象：hexo deploy 显示成功，网站却还是旧内容。

原因：deployer.js 里写死了 git push -u <repo> HEAD:main --force；实测三次 force push 一次都没触发构建。

解法：部署后去 Settings → Pages 重新 Save 一次，或走路径 B 的 POST /pages/builds。

顺带一个坑：Actions 里的「Re-run all jobs」是重放旧运行，认死原来那个 commit（实测重跑了一次，它执意发布的是一个只有 .gitignore 的空提交）。要新内容必须让 HEAD 动。

6.4 background 写成 url(...) 会生成坏链接

现象：页面背景不显示，源码里是 background-image: url(/url(/img/bg.jpg))。

原因：主题的 getBgPath() 会自己包一层 url()，你再写 url() 就套了两层，前面的 / 还会被 url_for 拼进去。

解法：只写纯路径。

6.5 副标题的 effect 语义是反的

现象：按注释写 effect: true（Typewriter Effect）结果副标题不显示，或者莫名依赖 CDN。

原因：模板里是 if (!{effect}) —— 那个 ! 不是 JS 取反，是 Pug 的非转义插值语法。effect: false 生成 if (false) 反而走静态分支；effect: true 会去 cdn.jsdelivr.net 拉 typed.js。

解法：要静态文字就写 effect: false。国内网络建议静态，别赌 CDN 能加载。

6.6 Pages 首次构建只建了个空提交

现象：仓库说有 Pages，访问却全站 404，连 /index.html 都 404。

原因：Pages 只在启用时构建了那个只有 .gitignore 的初始提交，之后的内容推送因故没触发新构建。

解法：让它从当前 HEAD 重新构建（路径 B 的 POST /pages/builds，或在网页上做一次真实提交）。

6.7 改了东西「没变化」

90% 是浏览器缓存，尤其是 favicon（Chrome 能缓存好几天）。

判断方法：无痕窗口打开，或直接访问单个资源 URL（/img/favicon.png）。无痕里正常 = 纯缓存问题，Ctrl + F5 或清站点数据即可。

7. 验收清单（部署后逐条过）

最后一条容易被忽略：把 2.8 MB 的原图直接丢进 source/img/ 会一起打包发布，站点体积会从 0.95 MB 涨到 3.7 MB。发布前先压缩（头像 400×400 / 37 KB 足够）。

8. 后续演进

| 阶段 | 做什么 | 收益 |

| — | — | — |

| 现在 | Hexo + Butterfly + Pages | 零成本、可写文章 |

| 下一步 | 换成 GitHub Actions 自动构建 | push 即上线，不依赖本地 |

| 再下一步 | 买 .com 域名 + 绑 Pages | 品牌化、可迁移 |

| 可选 | 加评论（giscus / Waline）、搜索、访问统计 | 互动性 |

关于自定义域名，两条硬提醒：

  1. 别用免费后缀（cc.cd、de5.net、eu.org 之类），整段被封的例子太多。

  2. 域名解析要指向 Pages 的四个 IP（185.199.108-111.153），并在仓库 Settings → Pages 里填 Custom domain，然后开 Enforce HTTPS。

最后：一个反直觉的经验

这套东西真正难的不是「怎么搭」，而是**「搭好了为什么国内打不开」**。

所以顺序应该是：

  1. 先用 github.io 直链跑通（国内实测可连）

  2. 确认能开、能发文章

  3. 再考虑自定义域名和高级托管

反过来做（先折腾 Vercel + 免费域名），你会在「明明部署成功了却打不开」上耗掉一整天，而且最后大概率还得退回来。
